  <name>Task 1: Modelo PlanoComissao + enum PlanoTipo + migração</name>
  <files>prisma/schema.prisma, prisma/migrations</files>
  <action>
Adicionar ao `prisma/schema.prisma`:

1. Enum `PlanoTipo` com os 4 valores EXATOS do domínio (não os nomes do research):
   `percentual_fixo`, `progressivo_atingimento`, `fixo_variavel`, `por_calls`.

2. Modelo `PlanoComissao` seguindo as convenções de tipo já travadas no topo do
   schema (comentário "CONVENÇÕES DE TIPOS"):
   - `id String @id @default(cuid())`
   - `colaboradorId String` + relação `colaborador Colaborador @relation(fields: [colaboradorId], references: [id])`
   - `tipo PlanoTipo`
   - `config Json` → Postgres JSONB (a forma da config NÃO é validada pelo Postgres; é
     validada por Zod na camada de domínio — ver ARCHITECTURE.md "Why config-driven JSONB").
     Documentar em comentário as formas esperadas por tipo:
       * percentual_fixo:          { percentual: number }           (ex.: 0.03)
       * progressivo_atingimento:  { faixas: [{ deAtingimento: number, percentual: number }] }
       * fixo_variavel:            { valorFixo: number, percentualVariavel: number }
       * por_calls:                { valorPorCall: number }         (e/ou faixas por nº de calls)
   - `vigenciaInicio DateTime @db.Date` (mês/dia de início da vigência; DATE, nunca timestamp)
   - `vigenciaFim DateTime? @db.Date` (NULL = plano vigente atual)
   - `createdAt DateTime @default(now()) @db.Timestamptz`
   - `updatedAt DateTime @updatedAt @db.Timestamptz`
   - `@@map("plano_comissao")`
   - Índice único parcial garantindo UM plano aberto por colaborador:
     `@@unique([colaboradorId], name: "plano_comissao_vigente_uq")` NÃO serve (fecha para
     sempre). Prisma não suporta índices parciais nativamente no schema; portanto adicionar
     o índice único parcial via SQL bruto DENTRO do arquivo de migração gerada (ver passo 4):
     `CREATE UNIQUE INDEX plano_comissao_vigente_uq ON plano_comissao (colaborador_id) WHERE vigencia_fim IS NULL;`
   - Índice normal: `@@index([colaboradorId])`.

3. Em `model Colaborador`, adicionar a back-relation (descomentar/atualizar o bloco de
   comentário "Fases futuras conectam aqui"): `planosComissao PlanoComissao[]`.

4. Gerar a migração com `npx prisma migrate dev --name add_plano_comissao` (o executor
   roda contra o Neon ao vivo). Depois de gerada, EDITAR o arquivo SQL da migração para
   acrescentar o índice único parcial descrito no passo 2 (Prisma não o emite sozinho),
   e re-aplicar (`npx prisma migrate dev` de novo aplica a alteração como nova migração,
   OU editar antes de aplicar — preferir: gerar com `--create-only`, editar o SQL para
   incluir o índice parcial, depois `npx prisma migrate dev` para aplicar).

Regra de dinheiro/percentual (PITFALLS.md): a `config` é JSONB e nesta fase só ARMAZENA
números; a validação de que são decimais válidos fica no Zod (Task 2). Não converter para
float em lugar nenhum — os números da config representam percentuais (ex.: 0.0125) e
valores em R$; o motor da Fase 5 os consumirá com precisão decimal.
  </action>
  <verify>`npx prisma migrate status` mostra a migração aplicada; `npx prisma generate` sem erro; o SQL da migração contém `CREATE UNIQUE INDEX plano_comissao_vigente_uq ... WHERE vigencia_fim IS NULL`.</verify>

<task type="auto">
  <name>Task 2: Schemas Zod discriminated-union por tipo de plano</name>
  <files>src/server/actions/planos-comissao.schemas.ts</files>
  <action>
Criar `src/server/actions/planos-comissao.schemas.ts` (arquivo SEM "use server" — mesmo
motivo de produtos.schemas.ts: um arquivo "use server" só pode exportar funções async).

Definir, com Zod v4:

1. Um helper `percentualSchema` = `z.number().min(0).max(1)` (percentuais são frações:
   0.03 = 3%, 1 = 100%; permitir >1 apenas se o domínio exigir — manter min 0, e para
   progressivo permitir até, digamos, 5 para tolerar bônus; documentar a escolha em
   comentário). `valorSchema` = `z.number().min(0)` para valores em R$.

2. Um schema por tipo (a `config` de cada um):
   - `configPercentualFixo` = `z.object({ percentual: percentualSchema })`
   - `configProgressivoAtingimento` = `z.object({ faixas: z.array(z.object({
       deAtingimento: z.number().min(0), percentual: percentualSchema
     })).min(1) })` — faixas arbitrárias definidas pelo admin; ordenadas por deAtingimento
     (validar com `.refine` que a lista está em ordem crescente de deAtingimento e sem
     duplicatas — o executor decide a mensagem).
   - `configFixoVariavel` = `z.object({ valorFixo: valorSchema, percentualVariavel: percentualSchema })`
   - `configPorCalls` = `z.object({ valorPorCall: valorSchema })` (nesta fase apenas valor
     por call; faixas por nº de calls podem entrar depois sem quebrar o discriminador).

3. `planoConfigSchema = z.discriminatedUnion("tipo", [...])` onde cada membro é
   `z.object({ tipo: z.literal("percentual_fixo"), config: configPercentualFixo })`, etc.,
   usando os 4 literais EXATOS do enum PlanoTipo.

4. `criarPlanoComissaoSchema` = objeto que estende o discriminated union com
   `colaboradorId: z.string().min(1)` e `vigenciaInicio: z.string()` no formato "YYYY-MM-01"
   (validar com regex ou z.iso.date + refine para dia 01; mês de referência é sempre o
   primeiro dia do mês — ver ARCHITECTURE.md). Como discriminatedUnion não permite
   `.extend` diretamente sobre a união, usar `z.intersection` ou aplicar os campos comuns
   em cada membro; o executor escolhe a forma que o Zod v4 aceitar (checar a doc do Zod v4
   se necessário) — o importante é ter um único schema exportado que valida
   {colaboradorId, vigenciaInicio, tipo, config}.

5. Exportar tipos inferidos: `export type PlanoConfig = z.infer<typeof planoConfigSchema>`
   e `export type CriarPlanoComissaoInput = z.infer<typeof criarPlanoComissaoSchema>`.

Nenhum import de Prisma Client aqui além de, se conveniente, o enum `PlanoTipo` de
@prisma/client como fonte única dos literais (opcional — z.literal com strings também
serve, mas se usar o enum, garantir que os literais batem).
  </action>
  <verify>`npx tsc --noEmit` sem erros no arquivo; um teste rápido mental/REPL: `criarPlanoComissaoSchema.parse({colaboradorId:"x", vigenciaInicio:"2026-07-01", tipo:"percentual_fixo", config:{percentual:0.03}})` passa e `{...tipo:"percentual_fixo", config:{valorFixo:1}}` falha.</verify>
  <done>Existe um discriminated union Zod que valida a config dos 4 tipos de plano; config de tipo errado é rejeitada; schema de criação exige colaboradorId e vigenciaInicio (YYYY-MM-01).</done>
</task>
