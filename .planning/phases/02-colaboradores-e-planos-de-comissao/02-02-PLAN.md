<objective>
Construir o coração da Fase 2: o serviço de versionamento de plano de comissão (COLAB-06)
que, ao definir/trocar o plano de um colaborador, FECHA a vigência anterior e ABRE uma nova
linha — sem nunca reescrever o histórico — mantendo a invariante de "um único plano aberto
por colaborador". Isso viabiliza os 4 formatos (COLAB-02..05) como dados versionados que o
motor da Fase 5 vai consumir por mês de referência.

Purpose: É a regra que impede a "reescrita silenciosa de histórico" (PITFALLS.md Pitfall 4/5
aplicado a planos). É lógica de negócio pura com entrada/saída definidas → TDD: dá pra
escrever `expect(depoisDeTrocar).toHaveClosedPreviousVigencia()` antes de implementar.

Output: repo de plano_comissao, service `definirPlanoComissao` transacional e versionado,
com suíte de testes que trava o comportamento de versionamento e validação.
</objective>

  <behavior>
Regras (COLAB-06) que os testes devem travar:

1. PRIMEIRO PLANO: colaborador sem nenhum plano → `definirPlanoComissao({colaboradorId,
   tipo, config, vigenciaInicio})` cria UMA linha com `vigenciaFim = null`.
   Caso: nenhum plano existente + input válido → 1 linha aberta, config gravada, tipo correto.

2. TROCA DE PLANO (o crux do COLAB-06): já existe um plano aberto → definir um novo:
   - fecha o anterior gravando `vigenciaFim` = (dia anterior ao novo vigenciaInicio, ou o
     próprio vigenciaInicio conforme a convenção escolhida — o executor decide e documenta;
     recomendação: `vigenciaFim` do antigo = `vigenciaInicio` do novo menos 1 dia, para não
     haver sobreposição nem buraco). Constraint do banco exige `vigencia_fim > vigencia_inicio`.
   - cria a nova linha com `vigenciaFim = null`.
   - AMBAS as operações na MESMA transação (`db.$transaction`) — se a criação da nova falhar,
     o fechamento da anterior é revertido.
   - a linha antiga NÃO é deletada nem tem sua config/tipo alterados (histórico intacto).
   Caso: 1 plano aberto tipo percentual_fixo → definir progressivo_atingimento →
   resultado: 2 linhas; a antiga com vigenciaFim preenchido e config original inalterada; a
   nova aberta com a nova config.

3. INVARIANTE 1-ABERTO: depois de qualquer operação, `count(planos where vigenciaFim=null
   and colaboradorId=X) === 1`. (O índice único parcial do banco é a rede de segurança; o
   service deve fechar o anterior ANTES de abrir o novo para não violar o índice.)

4. VALIDAÇÃO DE CONFIG POR TIPO (COLAB-02..05): antes de gravar, validar {tipo, config} com
   `planoConfigSchema` (do plano 01). Casos:
   - percentual_fixo + {percentual:0.03} → ok
   - progressivo_atingimento + {faixas:[{deAtingimento:0,percentual:0.005},{deAtingimento:0.7,
     percentual:0.01},{deAtingimento:1.1,percentual:0.015}]} → ok
   - fixo_variavel + {valorFixo:2000, percentualVariavel:0.01} → ok
   - por_calls + {valorPorCall:15} → ok
   - percentual_fixo + {valorFixo:1} (config do tipo errado) → REJEITADO (lança/erro), nada
     é gravado.

5. LISTAGEM DE HISTÓRICO: `listarPlanosDoColaborador(colaboradorId)` retorna todas as
   vigências ordenadas (mais recente primeiro ou por vigenciaInicio — documentar), para a
   UI de histórico do plano 03. `getPlanoVigente(colaboradorId)` retorna o plano aberto (ou
   null).

Cases (input → expected):
  - (sem plano) definir percentual_fixo(0.03) vig 2026-07-01 → [1 aberto, percentual_fixo]
  - (1 aberto percentual_fixo) definir progressivo vig 2026-08-01 → [antigo fechado (vigFim=2026-07-31), novo aberto progressivo]
  - definir com config incompatível com tipo → erro, 0 gravações
  - após troca → getPlanoVigente = novo; listarPlanos = 2 itens
