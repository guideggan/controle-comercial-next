  <behavior>
    Módulo PURO (zero imports de `@/lib/db`, Prisma, Next, ou `server-only`).
    Trabalha só com tipos primitivos/estruturas passadas como argumento — o
    service do plano 04-02 é quem busca do banco e monta a entrada.

    Tipo de entrada (uma linha por parcela já filtrada/normalizada pelo caller):
    ```ts
    export type RecebimentoParcela = {
      parcelaId: string;
      vendaId: string;
      tipo: "ENTRADA" | "MENSALIDADE" | "AVISTA";
      mesReferencia: string;      // competência "YYYY-MM-01"
      status: "PENDENTE" | "PAGO";
      valorRecebido: number | null; // number puro (Decimal já convertido pelo caller); null quando pendente
      closerId: string;
      sdrId: string | null;
    };
    ```

    Função principal:
    ```ts
    export function agregarRecebidoNoMes(
      recebimentos: RecebimentoParcela[],
      mesReferencia: string, // "YYYY-MM-01"
    ): ResultadoRecebidoNoMes
    ```

    `ResultadoRecebidoNoMes` deve conter, no mínimo:
      - `total: number` — soma de `valorRecebido` de todas as parcelas com
        `status==="PAGO"` E `mesReferencia===` o mês pedido. Entrada, mensalidade
        e à vista somam da mesma forma (a entrada comissiona igual à mensalidade,
        confirmado em PROJECT.md).
      - `porCloser: Record<string, number>` — total agrupado por `closerId`.
      - `porSdr: Record<string, number>` — total agrupado por `sdrId` (ignora
        parcelas cujo `sdrId` é null; a venda sem SDR não entra em nenhum bucket
        de SDR).

    Regras de correção (as que os testes travam):
      1. PGTO-03 — parcela `PENDENTE` conta como ZERO: nunca é somada, mesmo que
         `valorRecebido` esteja preenchido por acidente. O gate é `status==="PAGO"`.
      2. Competência: só entram parcelas cujo `mesReferencia` é EXATAMENTE o mês
         pedido (comparação de string "YYYY-MM-01"), nunca derivada de outra data.
      3. NÃO-DUPLA-CONTAGEM (PGTO-02, o coração da fase): cada `parcelaId`
         contribui NO MÁXIMO UMA VEZ para `total`. A soma por colaborador é
         apenas um reagrupamento das MESMAS parcelas — a soma de `porCloser`
         (das parcelas com closer) é consistente com `total`; nenhuma parcela é
         contada tanto como entrada quanto como mensalidade (são linhas
         distintas, uma por evento de pagamento). Se o caller passar a mesma
         parcela duas vezes (mesmo `parcelaId`), a função deve deduplicar por
         `parcelaId` (defensivo contra joins que fan-out).
      4. Dinheiro em `number` puro; somar valores crus e NÃO arredondar por
         parcela (arredondamento é responsabilidade do motor/Fase 5, no total).
         Não usar float trickery — soma simples de Decimal-as-number já vinda do
         banco basta nesta camada (o caller converte Decimal→number uma vez).

    Casos de teste (input → saída esperada), no mínimo:
      - Mistura de ENTRADA + MENSALIDADE + AVISTA, todas PAGO na mesma
        competência → `total` = soma exata; entrada NÃO é contada duas vezes.
      - Uma parcela PENDENTE com `valorRecebido` preenchido → contribui ZERO.
      - Parcela de outra competência (mês diferente) → NÃO entra no total.
      - Duas vendas de closers diferentes → `porCloser` separa corretamente e
        `total` = soma dos dois.
      - Parcela com `sdrId=null` → não aparece em `porSdr`, mas entra em `total`.
      - Mesma parcela passada duplicada (mesmo `parcelaId`) → contada UMA vez
        (prova explícita de não-dupla-contagem contra fan-out de join).
      - Lista vazia → `total=0`, `porCloser={}`, `porSdr={}`.
  </behavior>
